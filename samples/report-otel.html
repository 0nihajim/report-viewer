GenAI セマンティック規約の現状

OpenTelemetry では gen_ai.* 名前空間で LLM 呼び出しの属性が定義されている。ただし一部は Experimental のままで、バージョン間で属性名が変わる。計装コードで直接文字列を書くのではなく、定数へ寄せておくと改名時の影響を局所化できる。

主要な属性

  • gen_ai.system — プロバイダ識別子（openai, anthropic など）
  • gen_ai.request.model / gen_ai.response.model — 要求と実際の応答モデルは一致しない場合がある
  • gen_ai.usage.input_tokens / output_tokens — コスト算出の基礎

踏みやすい落とし穴

プロンプト本文の記録

プロンプトとレスポンスを span 属性に入れると、容易に属性サイズ上限に達し、Collector 側で切り捨てられる。切り捨ては警告なく起きるため、収集できている前提でダッシュボードを作ると後で破綻する。本文は span events かログに分離し、サンプリングを別に制御するのが実務的である。

プロンプト本文は PII を含みうる。記録の可否はデータガバナンス上の判断であり、計装の都合で決めてはならない。Collector で attributes/redact を挟み、SDK 側の設定漏れに依存しない構成にする。

ストリーミング応答の span 終了

ストリーミングでは最初のトークンが返った時点で処理は終わっていない。span を早期に終了させると TTFT と総レイテンシの区別がつかなくなる。ストリーム完了まで span を保持し、TTFT は個別の属性として記録する。

高カーディナリティ属性

プロンプトのハッシュやリクエスト ID をメトリクスのラベルに入れると、時系列数が線形に増えてバックエンドを圧迫する。これらは span 属性に留め、メトリクスのラベルはモデル名と結果区分程度に抑える。

Collector 設定例

processors:
  attributes/redact:
    actions:
      - key: gen_ai.prompt
        action: delete
      - key: gen_ai.completion
        action: delete
  batch:
    send_batch_size: 512

結論

span 属性に全部を詰め込む構成は早期に破綻する。量が必要なものはメトリクス、内容が必要なものはログ、因果が必要なものはトレースへ分けるという原則は、LLM アプリでも変わらない。

出典: OpenTelemetry Semantic Conventions (GenAI, Experimental)。属性サイズ上限は OTLP 既定値。プロンプト長と切り捨て率は自社 Collector ログ (2026-07、n=48,200) の実測。
