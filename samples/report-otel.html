OpenTelemetry で LLM アプリを可観測にする

LLM アプリケーションのトレーシングは、通常の Web サービスとは異なる難しさがある。 本レポートでは GenAI セマンティック規約の現状と、 実装時に踏みやすい落とし穴を整理する。

1. GenAI セマンティック規約の現状

OpenTelemetry では gen_ai.* 名前空間で LLM 呼び出しの属性が定義されている。 ただし 2026 年時点でも一部は Experimental のままであり、 バージョン間で属性名が変わる可能性がある点に注意が必要である。

1.1 主要な属性

  • gen_ai.system: プロバイダ識別子（openai, anthropic 等）
  • gen_ai.request.model / gen_ai.response.model
  • gen_ai.usage.input_tokens / output_tokens

2. 落とし穴

2.1 プロンプト本文の記録

プロンプトとレスポンスを span 属性に入れると、 容易に属性サイズ上限に達し、Collector 側で切り捨てられる。 本文は span events かログに分離し、 サンプリングを別に制御するのが実務的である。

プロンプト本文は PII を含みうるため、記録の可否はデータガバナンス上の判断が必要になる。

2.2 ストリーミング応答の span 終了

ストリーミングでは最初のトークンが返った時点では処理が終わっていない。 span を早期に終了させると TTFT と総レイテンシの区別がつかなくなるため、 ストリーム完了まで span を保持し、TTFT は個別の属性として記録する。

3. パイプライン構成

レイヤ役割備考
SDK計装・span生成自動計装は範囲を確認
Collector集約・属性加工・PII除去ここでフィルタを掛ける
Backend保存・検索高カーディナリティに注意

4. 設定例

processors:
  attributes/redact:
    actions:
      - key: gen_ai.prompt
        action: delete
      - key: gen_ai.completion
        action: delete
  batch:
    send_batch_size: 512

5. まとめ

トークン使用量とレイテンシはメトリクスとして、 プロンプト本文はサンプリングした上でログとして扱う分離が有効である。 span 属性に全部を詰め込む構成は早期に破綻する。
