LLM推論サーバの選定

プレフィックス共有率が40%を超えるワークロードでは SGLang が優位で、それ未満では vLLM が安定する。

計測構成
A100×1
モデル規模
14B
最大スループット差
2.3倍
SGLang 優位時

計測条件

入力1,024トークン・出力256トークンで固定し、同時リクエスト数を8から256まで変化させた。プレフィックス共有率は、リクエスト間で先頭から一致するトークン数の平均を入力長で割った値として定義する。

両者とも prefix caching を有効化しただけでスループットが改善する場合がある。比較の前に 設定の対称性を確認しないと、実装差ではなく設定差を測ることになる。

アーキテクチャの差

vLLM は PagedAttention により KV キャッシュを固定サイズのブロックに分割し、断片化を抑える。SGLang は RadixAttention でプレフィックスを共有するリクエスト間のキャッシュを再利用する。前者は入力が多様なときに効き、後者は入力が似ているときに効く。

共有率による逆転

共有率が低い領域では両者の差は5%以内に収まり、選定理由にならない。40%を境に SGLang が離れ始め、80%付近で2.3倍に達した。エージェント用途では会話履歴が共通プレフィックスになるため、この高共有率帯に入りやすい。

用途別の指針

ワークロード推奨理由
バッチ推論（入力多様）vLLM連続バッチングが安定
Few-shot プロンプト固定SGLangプレフィックス再利用が効く
エージェント（長い共通履歴）SGLang会話履歴の再計算を回避
構造化出力が必須SGLang文法制約デコードが高速

起動例

python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-14B-Instruct \
  --max-model-len 8192 \
  --gpu-memory-utilization 0.92 \
  --enable-prefix-caching

TTFT とスループットは同時に最適化できない。対話用途で TTFT を優先すると最大バッチサイズを下げる必要があり、総処理量は落ちる。どちらを指標にするか先に決めること。

結論

選定の分岐点はモデルでもハードウェアでもなく、ワークロードのプレフィックス共有率である。自社トラフィックの共有率を測れば、比較実験を回す前に候補は絞れる。

出典: 自社検証 (2026-07、A100 80GB×1、vLLM 0.9.x / SGLang 0.4.x)。数値は各条件3回試行の中位値。共有率はリクエストログ10万件からの実測分布に基づく。
