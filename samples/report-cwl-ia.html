結論を先に

CloudWatch Logs のコスト構造は取り込み・保管・クエリの三つに分解できるが、東京リージョンでは取り込みが圧倒的に支配的である。カスタムログの取り込みは 1 GB あたり 0.76 USD、保管は 1 GB-月あたり 0.033 USD なので、1 GB を取り込む費用は同じ 1 GB を約 23 か月保管する費用に等しい。[7] つまり保管側の最適化だけでは請求書は動かない。

2025 年に追加された Intelligent Tiering は 30 日／90 日アクセスなしでの自動階層化により保管費を下げるが、対象は保管費のみで、取り込み費には一切効かない。[3][6] 取り込み費を下げる手段は、ログクラスを作成時に Infrequent Access（以下 IA）にしておくこと、あるいはそもそも送らないこと、この二つしかない。

IA と Intelligent Tiering は競合しない。IA は「入口の単価」を半額にする作成時の決定、Intelligent Tiering は「置き場の単価」を後から下げるアカウント単位の設定であり、併用が正解になる場面が多い。

IA ログクラスの制約

制約は公式の機能対応表が正典である。[1] 発表時（2023 年 11 月）のブログの表とは既に差異があり、データ保護マスキングと取り込み時変換は当時「利用不可」だったが現在は IA でも対応している。[5][11][1] 発表ブログを根拠に判断すると過剰に制約を見積もることになる。

使える機能

IA でも維持される

  • フルマネージドな取り込みと保管[1]
  • Logs Insights QL（上記 4 コマンド以外の全て）[2]
  • OpenSearch PPL / SQL によるクエリ[1]
  • スケジュールドクエリ（S3 / EventBridge / ルックアップテーブルへ結果配信）[1][14]
  • 取り込み時変換（CloudWatch Pipeline）[1][12]
  • 機密データのマスキング[1][11]
  • KMS による暗号化[1]
  • クロスアカウント分析・集約[1]
  • S3 へのエクスポート／S3 Tables 連携（Iceberg）[1][13]

設計上の非対称性

  • アラームは「ログ内容」からは張れないが、スケジュールドクエリ + EventBridge で分単位の準リアルタイム検知は組める[14][15]
  • 外部への配信はサブスクリプション（ストリーム型）が使えないため、S3 Tables 連携かスケジュールドクエリ（バッチ型）に置き換える[13][14]
  • フィールドインデックスがないぶんスキャン費が効くので、クエリは必ず時間範囲で絞る

最大の非可逆性はログクラスが作成後に変更できないことである。[1][4] 判断を誤った場合の是正は、新しいロググループを作って送信先を切り替え、古い方をリテンション満了で枯らす、という移行作業になる。ロググループ名を変えられない事情があるならさらに厄介で、命名規約に世代を含めておくと安全である。

API・IaC 上の指定

ログクラスは CreateLogGroup の logGroupClass で指定し、有効値は STANDARD / INFREQUENT_ACCESS / DELIVERY の三つである。省略時は STANDARD。[4] OpenTofu / Terraform では aws_cloudwatch_log_group の log_group_class に対応する。第三の DELIVERY クラスは Lambda ログを S3 / Firehose へ中継する専用で、CloudWatch Logs 内の保持は固定 2 日（API リファレンスは 1 日と記述しており記述に揺れがある）、Logs Insights も使えないため、本レポートの選択肢には含めない。[1][4]

IA ログクラスは中国および GovCloud を除く全リージョンで利用可能。[5] Intelligent Tiering は中東（バーレーン）と中東（UAE）を除く全商用リージョンで、アカウント×リージョン単位で PutStorageTierPolicy（CLI では aws logs put-storage-tier-policy --storage-tier INTELLIGENT_TIERING）で有効化する。[3]

どのログタイプに向くか

公式の指針は明快で、AWS 自身が「IA は機能が少ないが大多数のユースケースに適する」とコスト最適化ガイドで述べている。[6] 発表ブログはより具体的に、デバッグログ・Web サーバログ・IoT フリートの詳細ログ・コンプライアンス保持用ログを挙げている。[5] これを判定基準に落とすと、次の三つの問いに全て「いいえ」なら IA が正解になる。

  1. このログの内容を条件にアラームを鳴らす必要があるか（メトリクスフィルタ／異常検出）
  2. このログを外部システムへストリームとして流す必要があるか（サブスクリプションフィルタ）
  3. 障害対応中にこのログを Live Tail で追う運用があるか
ログタイプ判定根拠
VPC フローログIA 推奨量が最も出るうえ、用途は事後のフォレンジックと通信経路の裏取り。閾値監視は CloudWatch メトリクス側で足りる
ALB / NLB / CloudFront アクセスログIA 推奨可用性監視は ELB メトリクスが担当。ログは事後の 5xx 追跡やボット分析で、Logs Insights の集計だけで完結する
WAF ログ条件付き IAブロック傾向の分析は IA で十分。ただし特定シグネチャの即時 SOC 連携が要件なら Standard（サブスクリプション必須）
アプリの DEBUG / TRACE レベルIA 推奨発表ブログが名指しする代表例。[5] ERROR 以上を別ロググループの Standard に分離し、DEBUG 以下を IA に落とす二段構成が最も費用対効果が高い
アプリの ERROR / WARN レベルStandardメトリクスフィルタでエラー率をアラーム化する対象。量も少ないので IA にする旨みがない
監査・コンプライアンス保持ログIA 推奨照会頻度が低く長期保持。[5] Intelligent Tiering と併用すれば 90 日後に保管費も最安階層へ落ちる[3]
IoT / エッジデバイスの詳細ログIA 推奨台数×verbose で量が支配的、参照は事後のフォレンジック[5]
バッチ・ETL のジョブ実行ログIA 推奨失敗検知はジョブ側の状態遷移イベントで取れる。ログは原因調査時のみ読む
RDS / Aurora の一般ログ・スロークエリログIA 推奨スロークエリ分析は Logs Insights の集計クエリで完結。Database Insights が別途メトリクスを持つ
EKS / ECS コンテナ標準出力（Container Insights 経由）Standard 必須Container Insights のログ取り込みが IA 非対応[1]
Lambda 関数ログStandard 寄りLambda Insights が IA 非対応[1]。EMF でメトリクスを出す実装なら IA では成立しない
CloudTrail 管理イベントStandard危険 API 呼び出しのメトリクスフィルタ + アラームが CIS 系ベンチマークの定番要件
EMF でメトリクスを埋め込むログStandard 必須EMF が IA 非対応[1]

二段構成という実装

単一のログストリームを丸ごとどちらかに寄せる必要はない。実務で最も効くのは重要度でロググループを分割する設計である。ERROR 以上を Standard の小さなロググループへ、INFO 以下を IA の大きなロググループへ送れば、アラームとサブスクリプションは前者に、量は後者に集まる。CloudWatch エージェントや Fluent Bit の出力設定で分岐でき、アプリ側の変更は不要な場合が多い。

Vended ログは送信先ロググループを IA で作成しておけばよく、請求は VendedLogIA-Bytes として計上される。[6] なお、ログを CloudWatch Logs ではなく S3 や Firehose へ直送してもデリバリ課金（S3-Egress-Bytes / FH-Egress-Bytes）は発生するため、「S3 に直送すればタダ」ではないことに注意する。[18]

失った機能を代替する

Standard の機能IA での代替差分
メトリクスフィルタ + アラームスケジュールドクエリ（最短 15 分間隔の cron）+ EventBridge → Lambda / SNS[14][15]検知遅延が秒から分に。異常検知は自前のクエリ条件になる
サブスクリプションフィルタ → OpenSearch / SIEMS3 Tables 連携（Iceberg）で Athena / Redshift から参照[13]ストリームからバッチへ。S3 Tables 連携自体は追加料金なし[13]
サブスクリプションフィルタ → Lambda 加工取り込み時変換（CloudWatch Pipeline）で事前整形[12]取り込み後の再加工はできない。変換は不可逆[12]
Live Tail短い時間範囲の Logs Insights を反復リアルタイム性は失われる。Standard の小さなロググループを併設する方が実用的
FilterLogEvents による単純検索Logs Insights の filterスキャン量課金（東京 0.0076 USD/GB）が発生する[7]

S3 への定期エクスポートを恒常的なアーカイブ手段にするのは AWS 自身が非推奨としており、代替としてサブスクリプションを推奨している。[17] IA ではそのサブスクリプションが使えないため、アーカイブ目的なら S3 に逃がすのではなく、IA + Intelligent Tiering で CloudWatch Logs に置いたまま長期保持するのが素直な構成になる。

試算：30 TB/月の vended ログを 90 日保持

東京リージョン、VPC フローログ等の vended ログを月 30 TB 取り込み、リテンション 90 日で定常状態（保管 90 TB）とした場合の月額を、階層料金を適用して算出する。前提として 1 TB = 1,024 GB、圧縮率は考慮しない（AWS の課金対象バイト数をそのまま用いる）。

構成取り込み (USD/月)保管 (USD/月)合計 (USD/月)
Standard クラス + Standard 保管15,564.803,041.2818,606.08
IA クラス + Intelligent Tiering（90 日後 AIA 階層）8,560.64608.269,168.90
差分−7,004.16−2,433.02−9,437.18

取り込み内訳は Standard が 10 TB×0.76 + 20 TB×0.38 = 7,782.40 + 7,782.40、IA が 10 TB×0.38 + 20 TB×0.228 = 3,891.20 + 4,669.44 である。保管は全量が最安階層に落ちた理想状態を仮定しており（90 TB × 0.0066）、実際には直近 30 日分が Standard 階層に残るため保管費はこれより高くなる。この保管側の仮定は筆者の単純化であり、下限値である。それでも削減額の 74% が取り込み側から出ており、取り込み単価が支配的という冒頭の主張はこの試算でも変わらない。年額換算で約 113,246 USD の差になる。

アンチパターン

  • Intelligent Tiering を有効化したから取り込みも安くなったと考える。階層化は保管費のみに作用する[3]
  • 全ロググループを一律 IA にする。CloudTrail や ERROR ログのアラームが静かに作れなくなり、後戻りには作り直しが必要[1][4]
  • EMF を使っているアプリのログを IA に送る。メトリクスが出なくなる[1]
  • IA で節約した分をスキャン費で溶かす。フィールドインデックスが使えない[16]ため、時間範囲を絞らないダッシュボードクエリのコストが跳ねる
  • Intelligent Tiering 環境で不要なクエリを回す。StartQuery / FilterLogEvents / GetLogEvents / CreateExportTask はアクセスと見なされ、下位階層のデータが 30 日間 Standard 階層に戻る[3]
  • 2023 年の発表ブログの機能表を現在の制約として使う。マスキングと取り込み時変換は既に IA 対応済み[1][5][11]

明日から打てる手（優先順）

  1. Cost and Usage Report で DataProcessing-Bytes / VendedLog-Bytes の上位ロググループを特定する。usagetype 名は[6]の対応表にある通りで、IA へ移った分は DataProcessingIA-Bytes / VendedLogIA-Bytes に現れるので移行効果もそのまま検証できる
  2. 上位ロググループごとに前掲の三つの問い（アラーム／外部ストリーム／Live Tail）を通す。全て「いいえ」なら IA 候補
  3. Intelligent Tiering をアカウント×リージョン単位で有効化する。取り込み側の判断とは独立に、保管費だけが下がる。StoredBytes メトリクスの StorageType ディメンションで階層別の内訳を可視化できる（日次発行）[3]
  4. 新規ワークロードは最初から IA で作る。既存の是正は作り直しになるので、新設分の判断を誤らないことが最も効く
  5. アプリログは重要度でロググループを分割する。ERROR 以上を Standard、INFO 以下を IA
  6. IA へ移すロググループのうちアラームが必要だったものは、スケジュールドクエリ + EventBridge へ置き換える[14][15]
