背景

単発タスクの正答率を測る評価は、主要モデルが揃って90%を超えた時点で比較の道具として機能しなくなった。差が出ないのではなく、差が出る領域を測っていない。エージェントの実力はツールをどう選び、失敗からどう復帰するかに現れるが、最終回答のみを見る採点はその過程を捨てている。

ベンチマークスコアと実運用での信頼性の相関は、2026年前半の報告では r = 0.31 にとどまる。スコアは選定の根拠として弱い。

飽和の実態

飽和は平均値ではなく分散に現れる。上位10モデルのスコア標準偏差は、2年前の8.4ポイントから1.9ポイントへ縮小した。順位は入れ替わり続けているが、その入れ替わりはノイズと区別できない。

再現性の欠如

  • プロンプトの空白や改行の差で数ポイント動く報告が複数ある
  • ツール環境のバージョン差が結果を左右し、環境が論文に記載されない
  • 評価側LLMを使う場合、その判定バイアスが未検証のまま残る

手法の比較

四方式を、測れる能力・再現性・コストで並べた。コストは同一タスク100件あたりの相対値である。

軌跡ベース評価

最終回答ではなく、ツール呼び出しの順序と引数を含む実行軌跡を採点する。同じ正答に至っても、無駄な探索を9回繰り返した軌跡と2回で到達した軌跡を区別できる点が、単発評価との決定的な差である。

async def evaluate(agent, task, rubric):
    trace = await agent.run(task, record_trace=True)
    # ツール呼び出しの順序と引数まで含めて採点する
    score = await judge(trace.steps, rubric=rubric)
    return {"task": task.id, "score": score, "steps": len(trace.steps)}

軌跡採点は評価側LLMへの入力が長くなり、コストが単発比で3〜5倍に膨らむ。全件ではなく層化抽出での適用が現実的である。

実務への含意

モデル選定にベンチマーク順位を使うのは、上位帯では意味を持たない。自社タスクの軌跡を50件程度記録し、失敗の型を分類したうえで比較する方が判断材料になる。順位ではなく失敗の型を見るべきである。

結論

評価の対象は「正解したか」から「どう到達したか」へ移りつつある。ただし軌跡採点も評価側LLMのバイアスを引き継ぐため、少数の人手評価を校正用に併走させる設計が現時点では妥当である。
